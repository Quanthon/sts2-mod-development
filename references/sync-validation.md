# 四类内容的差异同步、验证和恢复

仅在启用卡牌、关键词、状态或遗物工作簿时使用。其他类型 Mod 使用公共需求记录，不执行本流程。

## 更新闭环

1. 运行 diff，可按 --kind 与 --key 限定。工作簿未改并不保证代码或素材未变；有明确实现/素材请求时仍检查对应实际文件。
2. 根据差异和已有代码实现。首次没有基线时全部待核验，已有内容也不能直接全量接受。
3. 核对相关机制、注册、生成路径、语言、素材策略和数字映射（工程启用时）。四类内容分开处理，卡牌无差异不等于状态或遗物无差异。
4. 按改动类型验证，保存真实报告。
5. record 记录设计、配置、实现文件及报告哈希；再 accept 所选类别和条目。

删除仅报告。发现删除时不能全类接受，使用 --key 接受其他完成项。真正删除或改 key 是单独的兼容迁移任务，核对存档、初始绑定和全部引用后实施；本工具没有自动删除命令。

关键词改名以新增/删除加疑似重命名提示呈现。由 Agent 与使用者确认名称关系，保留稳定 ID；旧快照继续报告删除，不能把提示当作已授权迁移。

## 验证与证据

构建、资源导出、运行时场景及恢复原则统一见 [公共验证](validation.md)。
这里额外核对内容的中英文、注册/池/初始绑定及工程已采用的数字映射。
record 的 skipped 必须写明用户要求和保留的检查，不能掩盖失败；reused 指明此前记录、适用边界和未变化路径；passed 需要实际场景结果。

## 进度与恢复

.moddev/progress.json 的 entries 按类别、标识保存状态。Agent 可为待处理项记录 design_provided、implemented、needs_information 和待补说明；record 才产生 verified 记录。
恢复任务时重新运行 diff，比较配置、设计和真实文件。verified 记录不等于永远有效；修改后重新审查并记录。
优先恢复所选内容，不重建环境、不覆盖设计、不自动重跑已完成全部行为测试。

证据机制防止误用旧记录，不是自动游戏测试器，也不能证明报告文字真实。Agent 必须确实执行约定检查后使用 record，并纳入该内容相关的代码、语言、注册、机制依赖和必要素材文件。
